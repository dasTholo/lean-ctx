# ADR-012: Task Identity and Lineage

**Status:** Accepted
**Date:** 2026-08-09
**Authors:** Architecture Team

## Context

lean-ctx currently carries several identifiers that are useful at different
scopes. `OclaRequestContext` in `rust/src/core/ocla/types.rs` carries
`request_id`, `session_id`, `agent_id`, `content_ref`, `tenant_id`, and
`trace_id`. The proxy extracts trusted lineage headers in
`rust/src/proxy/lineage.rs`, while the OCLA wire projection is defined by
`rust/src/core/ocla/wire.rs`. A2A task resources and the `ctx_task` tool also
have task-shaped identifiers in `rust/src/core/a2a/task.rs` and
`rust/src/tools/ctx_task.rs`.

Those identifiers do not currently provide one stable identity for the unit of
work that crosses Runtime, Control Plane, and Cloud boundaries. A request can
be retried, a session can contain many requests, and a trace can span several
execution units. Using any of those values as the durable task key would make
joins ambiguous and would encourage source content or deployment details to
leak into an external identifier.

The architecture needs one identity that is created before execution starts,
survives retries and delegation, supports parent/child task trees, and can be
sent to Cloud without sending the source prompt, file, command, or tool
output. It also needs a migration path for clients and persisted records that
know only the existing identifiers.

## Decision

### Canonical task identity

`task_id` is the canonical identity of one logical unit of work. The identity
belongs to the Runtime execution boundary and is established at the first
trusted ingress. Control Plane and Cloud consume and index `task_id`; they do
not create, replace, or reinterpret it.

The ingress adapters are the places that attach the identity to an execution
context:

- MCP and tool execution enter through `rust/src/server/call_tool.rs` and
  `rust/src/server/execute.rs`.
- CLI-originated work enters through `rust/src/cli/call_cmd.rs` and the shared
  CLI dispatch paths.
- Provider and gateway requests enter through
  `rust/src/proxy/forward/mod.rs` and `rust/src/proxy/lineage.rs`.
- Agent-to-agent work enters through `rust/src/core/a2a/a2a_compat.rs` and
  `rust/src/core/a2a/task.rs`.

An ingress creates a new root `task_id` when no trusted canonical task
identity is present. A trusted continuation may carry an already issued
canonical `task_id`; the Runtime validates it and preserves it. An arbitrary
legacy task-shaped value supplied by an untrusted client is retained only as a
compatibility alias while the Runtime creates the canonical identity. Cloud
never becomes the identity issuer.

### Parent and child semantics

Each logical task has one canonical `task_id`. Retries and transport
reconnections for that logical task reuse the same `task_id`, but receive a
new `request_id` for each attempt. A delegated or spawned sub-task receives a
new `task_id` and carries:

```text
parent_task_id = the direct parent's task_id
trace_id       = the parent's trace_id
```

The root task has no `parent_task_id` and starts a new `trace_id`. The child
does not reuse the parent's `task_id`; the parent pointer is what makes task
ownership and fan-out explicit. A trace therefore groups the complete task
tree, while `task_id` identifies one node in that tree. A trace may contain
many task IDs, and a task may produce many request IDs.

The Runtime rejects self-parenting, cycles, malformed parent identities, and
lineage depth or fan-out that exceeds the applicable bounded execution policy.
`request_id` is never used as a parent pointer. `session_id` and `agent_id`
describe the caller and executor, not task ancestry.

### ID format and bounds

Canonical IDs are opaque textual values with this format:

```text
task_<32 lowercase hexadecimal characters>
```

The value is 128 bits generated by a cryptographically secure random source.
Its maximum encoded length is 37 ASCII bytes. `parent_task_id` uses the same
format. The value contains no timestamp, tenant name, user name, agent name,
file path, prompt, command, model, provider, or other payload-derived data.

Consumers compare and store the value as an opaque string. They must not parse
the random portion, derive meaning from its prefix, or construct IDs by
concatenating application data. The bounded format is enforced at ingress and
at every wire boundary before an identity is accepted.

### Existing identifier mapping

Every Runtime event that participates in task accounting or lineage joins on
`task_id`. Existing identifiers remain available for their original scopes and
are mapped to the task rather than promoted to the canonical key.

| Existing identifier | Scope | Required relationship to `task_id` |
| --- | --- | --- |
| `request_id` | One ingress attempt, retry, or emitted request | Many request IDs may map to one task; each attempt gets a new request ID. |
| `session_id` | Long-lived CLI, editor, or logical session | One session may contain many tasks; the task record stores the originating session ID when available. |
| `agent_id` | Runtime, worker, or agent principal | One agent may execute many tasks; delegation changes the executor without changing the task tree rule. |
| `tenant_id` | Authenticated organization or customer boundary | Many tasks belong to one tenant; a tenant ID scopes access but never creates task identity. Local-only work may have a null tenant ID. |
| `trace_id` | Distributed timing and diagnostic trace | One trace groups a root task and its descendants; child tasks inherit it. It is not the durable task key. |

The mapping is carried in the task envelope and projected into the existing
OCLA context. The next contract revision adds `task_id` and optional
`parent_task_id` to the shared context while retaining the existing fields for
compatibility. In particular, the current fields in
`rust/src/core/ocla/types.rs`, the payload-free header handling in
`rust/src/proxy/lineage.rs`, and the envelope structures in
`rust/src/core/context_capsule.rs` remain readable during migration.

### Payload-free Runtime/Cloud boundary

The identity and lineage envelope crossing Runtime, Control Plane, and Cloud
contains task metadata only:

- `task_id` and, when applicable, `parent_task_id`;
- `request_id`, `session_id`, `agent_id`, `tenant_id`, and `trace_id`;
- `schema_version`, bounded lifecycle timestamps, and contract references;
- authenticated routing, policy, or evidence references that are separately
  permitted by their contracts.

The identity envelope does not contain raw prompts, file contents, shell
commands, tool arguments, tool output, model responses, or source snapshots.
An existing `content_ref` or evidence reference is an opaque reference or
digest, not permission for Cloud to dereference Runtime-local source. Any
future content transfer requires a separate contract with its own data
classification, consent, retention, and authorization rules; task identity
alone never authorizes it.

This permits Cloud to correlate execution receipts, enforce tenant scope, and
aggregate bounded operational facts without receiving the source material that
caused the task.

### Backward compatibility

Clients may omit `task_id`. The first trusted Runtime ingress generates one
before constructing the internal OCLA context or forwarding the request. The
generated value is included in internal receipts and subsequent Runtime/Cloud
messages. Existing clients continue to receive and send their current
`request_id`, `session_id`, `agent_id`, `tenant_id`, and `trace_id` fields.

During migration:

1. New readers accept an optional external `task_id`, validate it, and always
   materialize a canonical internal task identity.
2. New writers emit `task_id` while retaining the legacy identifiers.
3. Old readers ignore the additive task fields and continue to correlate on
   their existing identifiers.
4. A legacy record without `task_id` receives a generated task identity when
   it is first admitted to the new task pipeline; its original storage key is
   retained as a private compatibility alias, not encoded into the task ID.
5. Replays preserve the admitted task identity so a replay cannot create a
   second logical task merely because the old record lacked the field.

No client is required to send source content to obtain a task identity, and no
historical source payload is reconstructed solely to populate the new field.

## Consequences

Task-level joins become unambiguous across Runtime, Control Plane, Cloud,
ledger, receipt, and trace systems. Retries remain attributable to one task,
while child tasks and delegated work remain independently observable. Runtime
ownership prevents a cloud service or provider from silently changing the
identity used for audit and billing.

The cloud boundary can carry useful lineage and operational evidence without
carrying source material. The opaque bounded format reduces accidental data
leakage and makes IDs safe to expose in logs, subject to normal access
controls.

Every ingress and task-spawning path must now propagate a small amount of
metadata, validate parent relationships, and preserve aliases during
migration. Existing analytics that group only by `request_id`, `session_id`, or
`trace_id` need explicit task joins. A trace tree also introduces bounded
depth/fan-out enforcement and storage for parent relationships.

The decision does not make source content generally available to Cloud and
does not solve authorization or retention by itself. Those concerns remain
separate contracts that must reference the task identity.

## Alternatives Considered

Using `request_id` as the task identity was rejected because retries create new
requests and one task can produce multiple requests. It cannot represent a
stable parent/child task tree.

Using `session_id` was rejected because a session contains many unrelated
tasks and can outlive the process that executes them.

Using `trace_id` as the durable task key was rejected because traces describe
diagnostic spans and, after delegation, can intentionally contain multiple
logical tasks. Trace IDs also have a different lifecycle and sampling policy.

Using a content hash or a payload-derived identifier was rejected because it
couples identity to source availability, leaks information through equality,
and violates the payload-free Cloud boundary.

Allowing Cloud or a provider to issue task IDs was rejected because the
identity owner would then depend on network availability and an external
authority could change the join key after local execution had begun.
