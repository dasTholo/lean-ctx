# markdownai v1.0.0 Adoption-Audit — konsolidiert

## Executive Summary

- **MDAI_LIBRARY_ROOT:** Variante A (eliminieren via `source_root` absolut) ist im v1.0-Engine **nicht
  funktionsfähig** — die Engine resolved `@include`-Pfade file-relative, nicht `source_root`-relative
  (siehe Sektion 1 + library-root-audit). Empfehlung: **Variante B (Status quo) beibehalten**.
- **Findings-Update:** Alle 12 v0.1.1-Findings sind in v1.0 weiterhin gültig — **keine** wurde
  `obsolete-in-v1.0`. §9 ist `still-valid-with-new-mechanism` (write_enabled bleibt primary gate, neue
  granular controls daneben). Pro Finding ein 1-Satz-Detail in Sektion 2. §1 enthält einen Doc-Bug:
  closer ist `@end`, nicht `@endforeach`.
- **Action-Items für v0.1.3:** 5 doc-only updates (klein), 5 macro-author guidance items (mittel), 1
  Engine-Issue-Eintrag (groß). Sortiert nach Aufwand in Sektion 3.

### User-Decision-Rationale (2026-05-26)

User entschied: **Library-Root = B** (Variante B beibehalten — Audit-Empfehlung gefolgt; Variante A im
v1.0-Engine nicht realisierbar). **Action-Items = alle 12 Findings** im v0.1.3-Plan adressieren — maximale
Coverage. Damit landen sowohl die 3 migration=yes-Items (§2/§3/§5 macro-author guidance) als auch die 2
optional (§7/§9) und die 7 doc-only (§1/§4/§6/§8/§10/§11/§12) im Plan. §4 wird als upstream
markdownai-Engine-Issue getrackt (keine config-based Workaround möglich).

## Sektion 1: MDAI_LIBRARY_ROOT-Vergleich

Vollständige Vergleichstabelle + Smoke-Daten im Library-Root-Audit-Doc:
[`docs/mdai/audits/2026-05-26-mdai-library-root-audit.md`](2026-05-26-mdai-library-root-audit.md).

**Kurz-Summary:**

- Smokes 1+4 beide Varianten gleich (top-level macro calls triggern keine `@include`-Resolution).
- Smoke 2: A=FAIL (9 warnings, 2 critical ENOENT auf `hard-rules.md` + `tool-quick-ref.md`), B=PASS
  (`warnings: []`).
- Smoke 3: A=NOT-RUN (predicted FAIL aus Smoke-2-Evidence), B=PASS (5/5 Phasen, 0 ENOENT,
  `mdai-brainstorm`-Skill).
- Root-Cause Variante A: Engine konkateniert `directory-of-calling-file` + relative path. `source_root`
  aus security.json ist offenbar nur Security-Check-Root, nicht Resolution-Root.

**Empfehlung des Audits:** Variante B (Status quo) in v0.1.3 beibehalten. Variante A wäre nur via
Engine-Patch (neue Directive `@include-from-root` oder `source_root`-aware Resolution) realisierbar —
Engine-Roadmap-Material, nicht Adoption-Plan.

## Sektion 3: Action-Items für v0.1.3-Plan (sortiert nach Aufwand)

### Klein (doc-only, kein Code-Touch)

- **[Klein] §1 Findings-Doc-Korrektur:** `closer = @end` (nicht `@endforeach`/`@endswitch`/`@endif`) —
  Engine-Source `parser-blocks.ts:113` (`walkBody(state, 'end')`). Update
  `docs/mdai/findings/2026-05-25-mdai-v0.1.1-engine-constraints.md` §1.
- **[Klein] §6 Doc-Confirm:** v1.0 bestätigt `@render-template from=…to=…[force]@end` Syntax. Kein
  `output=`-Arg. Keine Änderung nötig, evtl. „verified against v1.0" Note im Findings-v2-Doc.
- **[Klein] §10 hard-rules.md:** Doku-Update in `mdai/core/hard-rules.md` zum npm-prefix PATH side-effect
  (Hinweis: kein engine code path, user-env-only).
- **[Klein] §11 Re-affirm:** Modus-A Prosa-Pointer convention bestätigt. Optional: 1-Zeilen-Note im
  Findings-v2-Doc.
- **[Klein] §12 Re-framing:** Original-Finding korrigieren — kein „global scope", sondern per-call
  wrapper synthesis in `call_macro.ts:71`. Doc-update im Findings-v2-Doc.
- **[Klein] §7 hard-rules.md (CI/Subagent):** Hinweis in `mdai/core/hard-rules.md`: MCP-Server erbt
  `MDAI_LIBRARY_ROOT` vom Spawn-Prozess. Bei isolierten Subagent-/CI-Spawns muss env explizit gesetzt
  werden (z.B. CI `env:`-Block, oder process-spawn-env in custom MCP-server-wrapper).

### Mittel (macro-author guidance, Library-Cookbook)

- **[Mittel] §3 Macro-Author-Guidance:** `{{var}}` NICHT als path-arg in `file.containsLine` verwenden
  innerhalb von `@define`. Stattdessen literal-paths übergeben oder path-checks an calling agent
  delegieren. Library-File: Eintrag in `mdai/core/lean-context-audit.md` oder neuem
  `mdai/core/macro-cookbook.md`.
- **[Mittel] §5 Macro-Author-Guidance:** `@date` nicht in `@set`-string-literal embeddeden. Stattdessen
  `{{ @date format='YYYY-MM-DD' }}` direkt am Point of Use (render-template args, markdown text). Plus
  separate Notiz zu T0.1-Befund „`@set` cannot be used as a pipe source" (write-outputs-Phase).
- **[Mittel] §8 Convention-Doc:** „Keine frontmatter in include-target-files" als explizite Convention
  in `mdai/skills/mdai-brainstorm/spec-directive-conventions.md` o.ä. Alternative: mitigation via
  filename-pattern (z.B. `_include-*.md` keine frontmatter).
- **[Mittel] §9 Cookbook-Eintrag:** `write_enabled: true` + neue v1.0 granular controls (`write_root`,
  `allowed_write_paths`). 1-Eintrag im macro-cookbook mit beiden Layer (legacy + new).
- **[Mittel] §2 Macro-Author-Guidance:** `@set` list-literals NICHT als `@foreach`-Source verwenden.
  Stattdessen `@list <file.yaml>` oder hardcoded comma-separated literal als Source. Plus Test-Pattern
  („any @set+@foreach pattern must be tested via call_macro before deployment"). Library-File: macro-cookbook.

### Groß (engine-issue oder konzeptionelle Architektur)

- **[Groß] §4 Engine-Issue:** `file.containsLine` (und verwandte `file.*`-Predicates) blockt
  unconditionally bei absoluten Pfaden außerhalb project-CWD. KEIN config-based Workaround.
  Action-Item: GitHub-Issue in markdownai für config-erweiterbaren `file.*`-Predicate-Pfad-Bypass
  (oder explizite `allow_data_paths`-Whitelist-Berücksichtigung in `filesystem.ts:30`). Falls
  Engine-Side nicht möglich: dauerhafte hard-constraint — alle macro-author guidance §3/§5 muss diesen
  Punkt referenzieren.
- **[Groß, optional] Variante-A-Path-Resolution Engine-Issue:** GitHub-Issue in markdownai für
  `source_root`-aware `@include`-Resolution (file-relative → source_root-relative). Würde Variante A in
  einem zukünftigen Release ermöglichen — Repo-Portabilität ohne env-var. Nur opportune wenn das Audit
  ein klares „Variante A wäre wertvoll, sobald Engine es kann" als Konsens etabliert.
