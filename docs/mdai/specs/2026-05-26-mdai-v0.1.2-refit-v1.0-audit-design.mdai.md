## 1. Goal & Scope

### 1.1 Goal

Zwei offene Fragen klären, bevor v0.1.3 (Dedup-Implementation + Library-Adoption)
geschrieben wird:

1. **MDAI_LIBRARY_ROOT-Entscheidung.** Ist die env-var nach dem markdownai
   v1.0.0-Release noch sinnvoll, oder kann sie durch die nativen v1.0-Mechaniken
   (`security.json` `source_root` + relative `@include mdai/...`) ersetzt werden?
   Datengetriebene Entscheidung durch je einen vollen `mdai-brainstorm`-E2E-Run
   pro Variante.

2. **Findings-Re-Validation.** Sind die 12 Engine-Constraints aus
   `docs/mdai/findings/2026-05-25-mdai-v0.1.1-engine-constraints.md` gegen die
   v1.0.0-Engine noch gültig, oder hat das v1.0-Release einige obsolet gemacht?
   Pro Finding: Status (`still-valid` / `obsolete-in-v1.0` / `workaround-deprecated`)
   + neue Empfehlung. Output ist ein eigenständiger Findings-v2-Doc.

### 1.2 Non-Goals

- Implementierung der MDAI_LIBRARY_ROOT-Migration (egal welche Variante gewinnt) → v0.1.3.
- Dedup-Implementation (Adoption der A–E-Optionen aus v0.1.2 Plan v1 P2) → v0.1.3.
- Engine-Source-Patches an markdownai (z.B. Built-in `MDAI_LIBRARY_ROOT`-Konzept,
  Walk-Up-Resolver für `mdai/`-Library) → upstream-PR-Backlog, kein v0.1.x-Scope.
- Update von `mdai-brainstorm` Skill-Body-Konventionen → v0.1.3 falls Findings-v2
  das nahelegt.
- Code-Edits an Library-Files in v0.1.2-refit selbst (außer temporär im
  Wegwerf-Branch `audit/no-mdai-root` für T0.1 Variante A).

### 1.3 Recherche-Befunde (Vor-Audit)

Diese Befunde motivieren den Audit, ersetzen ihn aber nicht:

- **markdownai v1.0.0 hat KEIN built-in `MDAI_LIBRARY_ROOT`-Konzept.** `ctx_search`
  über `markdownai/packages/` ergibt 0 Matches. v1.0 expandiert `${VAR}` generisch
  in `@include` / `@import` / `@copy` / `@mkdir` (Test:
  `markdownai/packages/engine/src/__tests__/include-import-skill-dir.test.ts`).
- **v1.0 hat KEINEN Walk-Up-Resolver für die `mdai/`-Library.** Die env-var ist
  weiterhin user-defined, wird nur durch generische `${VAR}`-Expansion aufgelöst.
- **v1.0 hat `source_root` / `data_root` / `allowed_source_paths`-Jail in
  `security.json`** (siehe `markdownai/README.md` §security). `source_root`-Werte:
  `"auto"` (= docDir), `"cwd"` (= process working dir), absoluter Pfad. Patterns
  in `allowed_*_paths` unterstützen `${VAR}`-Expansion.
- **Implikation für MDAI_LIBRARY_ROOT.** Die env-var ist weiterhin nötig, ES SEI
  DENN man ersetzt sie durch `source_root: "<absoluter Pfad>"` + relative
  `@include mdai/...`. Trade-off: kein env-var-Stolperdraht (Finding §7) vs.
  Library nicht-portabel zwischen Repos. Welche Variante besser ist, entscheidet
  der E2E-Run in T0.1.

## 2. Architecture

Vier Phasen, strikt sequentiell, jede Phase mit hartem User-Decision-Gate:

```
Phase 0  Adoption-Audit (NEU)
  T0.1  MDAI_LIBRARY_ROOT-Audit (Variante A vs B, je voller E2E-Run)
  T0.2  Findings-v2 (alle 12 Findings systematisch gegen v1.0)
  T0.3  Audit-Konsolidierung + User-Decision-Gate        ◄── HART

  T1    Findings-v2-Doc schreiben + commit; v1 als superseded markieren

  T2    Shared-Content-Audit + Per-Cluster-Decision

  T3-T5 Backup-Cleanup, §8.1–§8.3 Smoke-Update, User-Handoff
```

die §8.1–§8.3 Smoke-Daten, die Phase 3 für T19/T20-Abschluss braucht. Phase 3
konsumiert nur das Artefakt, statt eigene Runs zu fahren.

## 3. Phase 0 — Adoption-Audit

### 3.1 Task T0.1 — MDAI_LIBRARY_ROOT-Audit (E2E pro Variante)

**Ziel.** Datengetriebene Entscheidung zwischen Variante A (env-var eliminieren)
und Variante B (Status quo) durch zwei identische `mdai-brainstorm`-E2E-Runs.

**Variante A — env-var eliminieren:**

- `~/.markdownai/security.json`: `source_root: "/home/tholo/Scripts/lean-ctx"`
  (absoluter Pfad), `allowed_source_paths: ["/home/tholo/Scripts/lean-ctx/mdai/**"]`.
- Alle `mdai/**/*.md`: temporäre Sed-Substitution
  `@include ${MDAI_LIBRARY_ROOT}/` → `@include mdai/`,
  `@import ${MDAI_LIBRARY_ROOT}/` → `@import mdai/`.
- Edits im **Wegwerf-Branch** `audit/no-mdai-root` isoliert — kein Commit, kein
  Push. Branch wird am Ende von T0.1 gelöscht.
- `~/.zshrc` Export bleibt zunächst gesetzt (kein Schaden, wird nur nicht mehr
  referenziert).
- `env`-Argument in MCP-Calls weglassen.

**Variante B — Status quo:**

- Aktuelle Config (`source_root: "auto"` + `${MDAI_LIBRARY_ROOT}`-Globs).
- Aktueller Code (alle `@include ${MDAI_LIBRARY_ROOT}/...`).
- `env={"MDAI_LIBRARY_ROOT": "/home/tholo/Scripts/lean-ctx/mdai"}` in MCP-Calls.

**E2E-Protokoll pro Variante** (identisch, 4 Schritte):

1. `mcp__markdownai__list_phases(file="mdai/skills/mdai-brainstorm/body.mdai.md", cwd="<repo>")`
   → 5 Phasen sichtbar (`pre-context`, `dialog-rules`, `dialog-process`,
   `write-outputs`, `handoff`)?
2. `mcp__markdownai__resolve_phase(file=..., phase="pre-context", cwd=...)`
   → `warnings: []`, Content enthält gerenderte `lean-context.md` /
   `tool-quick-ref.md` / `hard-rules.md`?
3. Voller Brainstorm-Lauf mit Test-Topic „dummy-feature-x" → Spec wird unter
   `docs/mdai/specs/2026-05-26-dummy-feature-x-design.mdai.md` erzeugt,
   spec-self-review läuft ohne ENOENT/Macro-Fehler?
4. `mcp__markdownai__call_macro` auf 3 Bootstrap-Macros (`mdai_bootstrap`,
   `detect_mai_hook_version`, `lean_context_audit`) → `found: true`,
   `warnings: []` für alle drei?

**Output.** Vergleichstabelle in
`docs/mdai/audits/2026-05-26-mdai-library-root-audit.md`:

| Kriterium                            | Variante A (kein env) | Variante B (Status quo) |
| Setup-Cost (one-time)                | security.json edit    | env-var + zshrc-Export  |
| Setup-Cost (neuer Dev / CI)          | nur security.json     | env-var + shell-source  |
| Portabilität Library → andere Repos  | NEIN                  | JA                      |
| Subagent-env-Vererbung (Finding §7)  | nicht betroffen       | weiterhin Stolperfalle  |
| Smoke 1–4 Pass-Rate                  | <PASS/FAIL pro Step>  | <PASS/FAIL pro Step>    |
| Render-Output identisch zu Baseline? | <yes/no + Diff-Size>  | <baseline>              |

**Wegwerf-Branch-Cleanup.** Nach den Runs:
1. `git checkout feat-mdai`.
2. `git branch -D audit/no-mdai-root`.
3. `cp ~/.markdownai/security.json.pre-audit ~/.markdownai/security.json` (Revert).
4. `ctx_search "MDAI_LIBRARY_ROOT" mdai/` → bestätigt Library-Files unverändert.

**KEIN Code-Commit aus T0.1.** Nur Audit-Doc-Commit.

### 3.2 Task T0.2 — Findings-v2 (alle 12 systematisch)

**Ziel.** Pro Finding aus
`docs/mdai/findings/2026-05-25-mdai-v0.1.1-engine-constraints.md` entscheiden:
gilt der Workaround noch, oder hat v1.0 ihn obsolet gemacht?

**Methodik pro Finding** (Tupel via `ctx_session` action="finding" persistieren):

| § | Topic                                                            | Re-Test-Methode                                                                              |
| 1 | Closer-Syntax (`@end` / `@endforeach` / `@endswitch` / `@endif`) | Engine-Source-Read `markdownai/packages/parser/src/directives/*.ts`                          |
| 2 | `@set+@foreach+{{var}}` in `@define` via `call_macro`            | Minimal-Repro (3 Zeilen) gegen `call_macro` in v1.0                                          |
| 3 | `{{var}}` in `file.containsLine` via `call_macro`                | Minimal-Repro analog §2                                                                      |
| 4 | `file.containsLine` Cross-CWD blockiert                          | Test mit `allowed_data_paths: ["/home/**"]` → ist Workaround jetzt config-only?              |
| 5 | `@set var = "{{@date}}"` Parser-Bug                              | Minimal-Repro                                                                                |
| 6 | `@render-template from/to/force` Syntax                          | Engine-Source-Verify (`markdownai/packages/parser/src/directives/render-template.ts`)        |
| 7 | `${MDAI_LIBRARY_ROOT}` nicht expandiert bei standalone resolve   | Direkt durch T0.1 abgedeckt — Ergebnis übernehmen                                            |
| 8 | Frontmatter leakt in `mode:include`                              | Engine-Source-Read `markdownai/packages/engine/src/include.ts` (oder Äquivalent)             |
| 9 | `write_enabled: true` Pflicht                                    | v1.0 hat `write_root` + `allowed_write_paths` → Workaround in v1.0-Mechanik neu formulieren  |
| 10 | npm-prefix PATH                                                 | Unverändert (User-Env-Side-Effect)                                                           |
| 11 | Modus A vs B (Prosa-Pointer vs `@call`)                         | Design-Entscheidung — keine Re-Test, nur Re-Affirm                                           |
| 12 | Bootstrap-Macros via global scope                                | Engine-Source-Read `markdownai/packages/engine/src/` (Macro-Scope-Resolution)                |

**Pro Finding Output-Tupel** (vier Felder):

- `status`: `still-valid` | `obsolete-in-v1.0` | `workaround-deprecated` | `still-valid-with-new-mechanism`
- `v1.0-evidence`: 1-Zeilen-Verweis (engine-source-line oder smoke-result)
- `new-recommendation`: 1–2 Sätze, was in v0.1.3 / Adoption-Plan einfließt
- `migration-needed-in-v0.1.3`: `yes` / `no` / `optional`

**Aufwand-Estimate.** ~1.5h für 12 Findings (5–10 min pro Finding, Engine-Reads
und minimal-Repros).

**Subagent-Split.** T0.2 wird in zwei parallele Subagent-Dispatches gesplittet
(Findings §1–§6 und §7–§12, je `sonnet`). Beide Subagents persistieren ihre
Tupel in `ctx_session`. T0.3 verifiziert dass 12 Tupel vorliegen bevor er die
Konsolidierungs-Doc schreibt.
