# lean-ctx: The Definitive Narrative

## Core strategic decision

**Do not sell lean-ctx as a token saver. Sell it as the context layer for
software agents.**

Token savings are a measurable consequence of better context. The real promise
is larger: an agent that sees the right code, carries forward what it learned,
works in concert with other agents, and remains governable at scale.

This is a category story, not a feature inventory:

> **From stateless tools to an operating intelligence for software agents.**

The homepage should make one claim per scroll, show one inspectable product
artifact per claim, and repeat one primary action: **Install for your agent.**

---

## 1. The five-act website narrative

### Act 1 — The problem: agents are brilliant, but they start blind

Today's coding agents have a paradoxical failure mode: they can reason over an
enormous context window, yet they waste that capacity rereading repositories,
parsing noisy terminal output, and rediscovering decisions made yesterday.

Every new conversation is a cold start. Every extra tool call is raw text.
Every handoff loses context. Every multi-agent workflow creates more isolated
copies of the same incomplete understanding. Bigger windows merely let the
noise travel farther.

The result is not only higher token spend. It is slower debugging, weaker
decisions, brittle collaboration, and a fleet that cannot be audited or
governed.

**Visitor thought:** “Yes. My agent is capable, but it keeps doing the same
work and missing the shape of the codebase.”

**Narrative turn:** The problem is not that agents need more context. They need
better context.

### Act 2 — The insight: context is infrastructure

Code is not a pile of text. It has symbols, calls, dependencies, tests,
ownership, history, policies, and decisions. Agent context should preserve that
structure instead of flattening it into a prompt.

The winning agent stack will not be the one that can afford the largest context
window. It will be the one that can decide what matters, retain what it learns,
and prove what it did.

That requires a layer between the agent and everything it reads, searches,
executes, remembers, and shares.

**The category definition:**

> **Context engineering is the discipline of turning codebase reality into the
> smallest, highest-signal, policy-safe working memory an agent needs to act.**

**Visitor thought:** “This is not prompt trimming. This is the missing runtime
between the agent and my engineering system.”

### Act 3 — The product: lean-ctx is the context layer

lean-ctx sits between coding agents and the codebase, tools, and knowledge they
use. It works locally by default and changes the quality of every interaction.

1. **Read with structure.** AST-aware read modes, repository maps, search, and
   compressed shell output replace indiscriminate file dumps with task-relevant
   context.
2. **Remember across time.** A knowledge graph, session continuity, snapshots,
   and provider data stop each conversation from becoming a new cold start.
3. **Coordinate across agents.** A registry, agent bus, handoffs, and shared
   decision trail let a multi-agent team work from one evolving intelligence.
4. **Govern with evidence.** Policies, sensitivity controls, budgets, leases,
   compliance reporting, and a signed savings ledger make agent work
   inspectable and defensible.
5. **Understand the codebase.** Call graphs, impact analysis, intent detection,
   import resolution, and quality analysis give agents structural awareness—not
   merely shorter text.

The transparent proxy, prefix caching, and token compression are essential.
They are simply the receipt generated by a smarter system.

**Visitor thought:** “I can install this now for a better coding loop, then
grow into memory, coordination, and governance when my team needs it.”

### Act 4 — The proof: make every claim inspectable

Do not ask visitors to trust a percentage. Let them inspect the evidence.

- Switch a real source file between `full`, `map`, and `signatures` views.
- Show what was retained, what was deferred, and how to expand it again.
- Run a real command through compressed shell output.
- Display the agent's context timeline: read → search → decision → handoff.
- Link every public savings number to its corpus, tokenizer, mode, date, and
  reproduction command.
- Show the Ed25519-signed ledger as proof that savings and policy events were
  recorded, not asserted.

The proof hierarchy is deliberate: **product artifact → reproducible benchmark
→ local-first architecture → open source → customer outcome.** Do not use a
logo wall without explicit permission and attributable results.

**Visitor thought:** “I can see the mechanism, reproduce the claim, and verify
what runs where.”

### Act 5 — The action: start with the agent already on your machine

The closing message is not “book a demo.” It is: **choose your agent and make
its next read better.**

Offer a persistent selector for Cursor, Claude Code, Codex, Windsurf, Copilot,
and Other. Once selected, the site adapts every install command and CTA. The
first win must be visible in minutes: install, run a read or search, inspect the
before/after result, and keep building.

For teams, the secondary path is clear: evaluate the context layer as shared
infrastructure—memory, coordination, policy, and evidence included.

**Visitor thought:** “This is concrete. I know exactly what to do next.”

### Homepage: the funnel

The homepage creates urgency and removes adoption risk. It must not attempt to
teach every feature. Its order is: **problem → live proof → category/product →
trust → install.** The only prominent CTA is **Install for [selected agent]**.
Deeper pages are for mechanism and evaluation.

### How it works: the mechanism

Open with a single causal line: “Before an agent spends a token, lean-ctx
decides what deserves to enter its context.” Then demonstrate the loop:

1. Read structure, not a file dump.
2. Search and execute with signal-preserving results.
3. Record knowledge, share a handoff, and reuse the context next time.

End by routing technical visitors into docs, architecture, or the first
agent-specific setup.

### Pricing: the business model

Make the product boundary unmistakable: local open-source core first; any paid
team/enterprise control plane clearly labelled by what it adds. Do not price by
vague “AI credits.” Price the value layer visitors buy: shared memory,
governance, policy, compliance, support, deployment, and organization controls.

The page should turn finance anxiety into a concrete decision: “Here is the
baseline, here is the measured context reduction, here is what is verifiable,
and here is what the team layer changes.”

### Enterprise: the governance story

This page is not a longer feature page. It answers whether lean-ctx can become
trusted infrastructure. Lead with: **“Give agents access to context without
giving up control.”** Explain the local/default boundary, what optional hosted
or external providers do, policy enforcement, sensitivity controls, budgets,
leases, signed evidence, and compliance outputs. Market only capabilities that
are available now; isolate roadmap items visibly.

### Docs: the quickstart

Docs must feel like an invitation, not a reference archive. The first screen
asks the visitor's agent, shows one copyable command, shows expected output,
and offers one first task. The next page explains read modes only after the
visitor has experienced a better read. Keep the sequence: **install → verify →
first win → customize → deepen.**

## 5. Competitive narrative: the category distinction

Use these lines only where comparison is natural—comparison pages, sales
conversations, pricing evaluation—not as a hostile homepage fixation.

1. **Token compressors shrink what agents say. lean-ctx transforms what agents
   know.**
2. **Shorter prompts are useful. Better context changes the work itself.**
3. **Compression removes noise from a message. lean-ctx decides what should
   enter the message at all.**
4. **One tool trims a request. lean-ctx gives the next agent the last agent's
   understanding.**
5. **Saving tokens is an event. Building agent memory is an advantage.**
6. **A proxy can reduce traffic. A context layer can read, reason over
   structure, remember, coordinate, and prove.**

The honest qualifier:

> If all you need is smaller payloads, a compressor may be enough. If you need
> agents to improve over time, work together, and operate under control,
> lean-ctx is built for that job.

### Section 7 — FAQ

**Is lean-ctx just a token compressor?**

No. It reduces wasteful context, but its job is larger: structured code reads,
memory across sessions, multi-agent coordination, code understanding, and
governance with evidence.

**Will lean-ctx change my code?**

No. Its context layer helps agents read, search, and interpret engineering
information. Your normal edit and review workflow remains in control.

**Is compression lossy?**

Different tasks need different views. lean-ctx preserves structure, makes its
output inspectable, and lets the agent expand to fuller context when needed.
Public claims should always state their mode and measurement basis.

**Which agents work with lean-ctx?**

lean-ctx supports Cursor, Claude Code, Codex, and other compatible coding-agent
workflows. Choose your agent in the install flow for the exact setup path.

**Does my code leave my machine?**

Not by default. lean-ctx is local-first and zero-telemetry by default. If you
enable hosted features, external providers, or connectors, the product should
state the specific data boundary before you do.

**How do I prove the savings?**

Run the benchmark against your own repository and inspect the result. lean-ctx's
ledger and reproducible benchmark artifacts are designed to make performance
claims verifiable rather than promotional.

## Messaging guardrails

- Say **“context layer”** first; define **“context engineering”** immediately
  in plain language.
- Say **“read the right code”** before “AST,” “RRF,” “property graph,” or tool
  counts.
- Treat **token savings as a receipt**, never the only promise.
- Give each number a basis, date, tokenizer or measurement method, and a path
  to reproduce it.
- Keep product availability precise: local OSS core, optional hosted features,
  paid team/enterprise controls, and roadmap are never visually conflated.
- Use **Install for [agent]** as the recurring primary CTA. “Book a demo” is a
  valid secondary action only on Enterprise and high-intent evaluation paths.
- Keep the tone declarative and technical. No “revolutionary,” “magic,” or
  vague “AI-powered” language.
