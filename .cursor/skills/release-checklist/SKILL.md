# Release lean-ctx

Follow the phases in order. Treat preparation and publication as separate
authorities: do not create or push a tag when the user only asks to prepare or
check a release.

## Gather

1. Resolve the OSS root and intended SemVer `X.Y.Z`; reject a leading `v` in
   files and use it only for Git tags.
2. Read `docs/ga/release-checklist.md`, `.github/workflows/release.yml`, the top
   of `CHANGELOG.md`, and the `[package]` section of `rust/Cargo.toml`.
3. Check `git status`, current branch, both remotes, and existing local/remote
   `vX.Y.Z` tags. Stop on unrelated changes or a tag that already points
   elsewhere.
4. Locate packaging repos. Prefer explicit paths, then sibling defaults:
   `../homebrew-lean-ctx`, `../aur-lean-ctx`, and `../aur-lean-ctx-bin`.
5. Confirm release credentials, signing/checksum availability, and whether the
   request authorizes publish operations.

Run `scripts/verify-version.sh X.Y.Z [oss-root]` before tagging. After the
release artifacts exist, rerun it with `VERIFY_DISTRIBUTION=1` to include the
Homebrew and AUR repositories.

## Act

1. Bump the engine `[package]` version in `rust/Cargo.toml` and regenerate
   `rust/Cargo.lock` through Cargo; never hand-edit lockfile checksums.
2. Keep engine-shipping npm wrappers aligned:
   `packages/pi-lean-ctx/package.json` and
   `packages/lean-ctx-bin/package.json`.
3. Add the newest `CHANGELOG.md` section as `## [X.Y.Z] — YYYY-MM-DD` with only
   shipped, user-visible changes.
4. Prepare packaging metadata:
   - Homebrew is generated by the non-RC `update-homebrew` release job after
     `SHA256SUMS` exists. Verify its formula instead of inventing hashes.
   - In both AUR repos set `pkgver=X.Y.Z`, reset `pkgrel=1`, update source and
     binary checksums from published assets, then regenerate `.SRCINFO` with
     `makepkg --printsrcinfo > .SRCINFO`.
   - Do not promote release candidates to stable Homebrew or AUR channels.
5. Run the project quality gate from `rust/`:

   ```bash
   cargo test --lib
   cargo clippy --all-features -- -D warnings
   cargo fmt --check
   ```

6. Also run `python3 scripts/check-package-versions.py`,
   `python3 scripts/check-sdk-versions.py`, and any security/history gates
   required by `docs/ga/release-checklist.md`.
7. Commit the intentional version changes. Before any GitHub push, enforce the
   repository branch-count rule from `AGENTS.md`, then push the approved `main`
   commit to `github` and `origin`.
8. When publication is authorized, tag the approved commit once and push it:

   ```bash
   git tag vX.Y.Z
   git push github vX.Y.Z
   git push origin vX.Y.Z
   ```

9. Wait for release CI and required artifacts. Then push reviewed AUR commits;
   use the Homebrew CI result or a reviewed manual formula update if CI failed.
   Never bypass missing checksums or reuse/move a published tag.

## Verify

- Confirm GitHub release assets include platform archives, `SHA256SUMS`, SBOM,
  and `release-manifest.json`; run the release-integrity verifier.
- Confirm the Homebrew formula and both AUR package pages resolve to `X.Y.Z`
  and their hashes match published assets.
- Install or inspect one artifact per packaging channel and run
  `lean-ctx --version` plus `lean-ctx status`.
- Confirm `main` and `vX.Y.Z` exist on both required remotes and record the
  release commit, CI URLs, checksums, packaging commits, and exceptions.
- On failure, stop promotion, preserve evidence, fix on `main`, and publish a
  new patch tag; never weaken integrity checks.
