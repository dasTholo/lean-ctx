# Thinkery Intel Inside Partner Strategy

## Document purpose

This document defines the complete partner ecosystem for Thinkery.

It turns the Intel Inside insight into a repeatable commercial system.

Thinkery powers context intelligence for agents built by other people.

The strategy covers partner types, technical integration, economics, tiers,
enablement, co-selling, governance, and open-source protection.

The intended reader is a founder, product leader, partner executive, or
enterprise buyer deciding whether Thinkery should sit inside an agent stack.

The strategy is written as an operating design, not as a slogan.

## Executive thesis

Intel did not need to build every PC to become essential to the PC market.

It supplied a difficult, valuable subsystem that made many PC makers faster.

Thinkery can occupy the same position in the agent economy.

Agent builders own the workflow, user experience, and domain outcome.

Thinkery owns the context intelligence that makes those agents efficient,
durable, observable, and governable.

The partner does not have to become a context systems company.

The customer does not have to assemble compression, memory, governance, and
cost controls from disconnected tools.

The agent carries visible proof that its context layer is powered by Thinkery.

Every successful deployment creates another distribution surface for Thinkery.

Every new integration makes the context layer more useful to the next builder.

## The strategic promise

Thinkery is the context operating layer inside the agent ecosystem.

We make every serious agent more capable without owning every agent.

We make every agent deployment more economical without hiding the economics.

We make every agent deployment more auditable without slowing the builder.

We give partners a differentiated enterprise story they can sell repeatedly.

We give customers a neutral layer that can travel across models and tools.

We keep the core LeanCTX engine open so the ecosystem can inspect and extend it.

We commercialize the operational features that enterprises require at scale.

## Strategic design principles

Partner-first means the partner owns the customer outcome and relationship.

Neutral means Thinkery supports multiple model, cloud, IDE, and DevOps choices.

Measurable means every deployment can show a baseline and a delta.

Composable means a customer can adopt one module before adopting the suite.

Secure means context boundaries are explicit, tested, and enforceable.

Open means LeanCTX remains inspectable and useful without a commercial license.

Commercial means enterprise operations are paid when they create enterprise
value.

Repeatable means a partner can deploy the same kit across many customers.

Progressive means program benefits increase with verified capability and value.

## Technical meaning of Intel Inside

Intel Inside is a technical contract, not only a badge.

## The Thinkery context layer

The layer sits between agent orchestration and model invocation.

It receives context candidates, policies, identity, and task metadata.

It selects, compresses, retrieves, stores, and explains context.

It returns a governed context package to the agent runtime.

It emits telemetry for cost, quality, latency, memory, and policy.

It can run beside the agent, in a shared service, or in a customer-controlled
environment.

## Core technical contract

Input is a task, identity, policy set, context candidates, and model profile.

Processing is selection, ranking, compression, memory resolution, and policy
evaluation.

Output is context with provenance, budget metadata, and decision evidence.

Telemetry is a traceable record of what entered, changed, and left the layer.

Control is a versioned policy and configuration surface.

Recovery is an explicit fallback when a dependency or optimization path fails.

## Capability 1: compression

Compression removes redundant or low-value context before model invocation.

It preserves task-relevant meaning and records the transformation.

It can use summarization, deduplication, structure-aware reduction, or
reference-based retrieval.

It must respect data sensitivity and customer-defined quality thresholds.

It must expose the before-and-after context budget.

It must support a bypass path for workflows where lossless context is required.

### Compression partner value

Builders spend less time inventing prompt-budget heuristics.

Customers spend less on repeated or irrelevant input tokens.

Operators see where context waste originates.

Model partners receive cleaner, more intentional requests.

SIs can standardize an optimization method across agent projects.

### Compression safeguards

Every transformation has a strategy version.

Every transformation can be tested against an evaluation set.

Every transformation can be disabled by policy.

Every transformation reports quality and cost deltas.

Every transformation preserves a provenance link to source context.

## Capability 2: memory

Memory turns repeated context into governed, reusable state.

Thinkery distinguishes working memory, episodic memory, semantic memory, and
policy metadata.

The distinction prevents a useful fact from becoming an uncontrolled permanent
record.

Memory writes require an explicit reason, scope, owner, and retention rule.

Memory reads require identity and purpose-aware authorization.

### Memory partner value

Builders get durable behavior without building a memory subsystem.

Customers get deletion, retention, and access controls.

Operators can see whether memory improves outcomes or only increases cost.

SIs can package memory patterns by domain.

Distribution partners can operate memory as part of a managed service.

### Memory safeguards

No memory write occurs without a policy decision.

Sensitive data receives a stricter default retention path.

Customers can inspect and delete memory entries.

Memory provenance includes source, timestamp, and responsible workflow.

Memory isolation is explicit across tenants, users, matters, and agents.

## Capability 3: observability

## Reference architecture: embedded

The agent runtime imports a Thinkery client library.

The client applies context policies in the same process or deployment unit.

The runtime sends model-ready context through the client.

## Reference architecture: sidecar

The agent runtime calls a local Thinkery sidecar.

The model call can remain in the agent runtime or pass through a gateway.

This pattern isolates upgrades and supports polyglot agent stacks.

The partner can standardize deployment with a container or orchestration kit.

The customer can place the sidecar inside its controlled network boundary.

## Reference architecture: shared service

Many agents call a shared Thinkery context service.

## Reference architecture: control plane and data plane

rules.

The planes can be deployed together or separately.

## Integration acceptance criteria

The adapter passes authentication and authorization tests.

The adapter preserves source provenance.

The adapter handles policy denial correctly.

The adapter reports context and cost telemetry.

The adapter supports bounded fallback.

The adapter has an owner and version compatibility statement.

The adapter has a customer-safe diagnostic mode.

## Technical partner scorecard

Measure integration completion time.

Measure active production integrations.

Measure monthly context volume through the integration.

Measure supported customer environments.

Measure defect and escalation rate.

Measure time to resolve critical integration issues.

Measure developer adoption of the integration.

Measure partner-sourced qualified pipeline.

## Security and trust baseline

Every partner integration has a documented data-flow diagram.

Every partner identifies the data controller and data processor roles.

Every partner documents encryption in transit and at rest.

Every partner documents key management and rotation.

Every partner documents subprocessors and data residency.

Every partner documents deletion, retention, and incident processes.

Thinkery can suspend integrations that create material customer risk.

## Revenue model overview

Thinkery uses multiple revenue levers because partner value is not one-dimensional.

Platform fees monetize durable capability and availability.

Usage fees monetize variable context processing.

Certification fees monetize scarce assessment and enablement work.

Revenue share aligns marketplace kits and embedded distribution.

Success fees align measurable savings with partner-led outcomes.

The model should remain legible to customers and partners.

## Revenue model principle

Charge for durable platform value.

Charge for variable consumption when consumption drives cost or value.

Charge for scarce human assessment only when it creates a real qualification.

Share revenue when a partner creates attributable demand or distribution.

Share success when the measurement contract is clear enough to avoid disputes.

Do not stack every fee on every deal.

## Revenue stream 1: platform fee

The platform fee is a recurring fee per agent, tenant, or deployment class.

It covers control-plane access, policy management, supported integrations, and
base observability.

The exact unit can differ between direct, SI, MSP, and embedded contracts.

The unit must be easy for a buyer to forecast.

The unit must be difficult to manipulate through artificial agent splitting.

### Platform fee design

Use a minimum annual commitment for enterprise support.

Use a lower entry tier for builders validating one production workflow.

Price additional governance, residency, and support requirements explicitly.

Provide volume bands that reward real adoption.

Review the unit if customers create many nominal agents for one workload.

## Revenue stream 2: usage fee

The usage fee is tied to context processed through Thinkery.

Possible meters include input tokens processed, context events, memory reads,
memory writes, or governed requests.

The meter should align with Thinkery’s marginal cost and customer value.

The customer must be able to reconcile usage to its own telemetry.

Partners need a simple forecast model before committing to a resale price.

### Usage fee design

Publish a base meter and define included usage in each platform tier.

Use volume bands instead of opaque negotiated rates.

Allow a customer cap or budget policy.

Alert before a customer crosses an agreed threshold.

Do not charge twice for the same event because of internal retries.

## Revenue stream 3: certification fee

The certification fee covers an assessment of a partner’s people, process, and
deployment capability.

It is not a pay-to-play logo fee.

The fee includes assessment materials, review time, and a renewal cadence.

Thinkery may waive or credit the fee for strategic lighthouse partners.

Waivers must be recorded and must not lower the certification standard.

### Certification fee logic

Individual certification can be low-cost and exam-oriented.

Organization certification can include practical implementation review.

Advanced certification can include security, governance, and operations review.

Renewal can be fee-based when the scope requires reassessment.

Training and certification should be priced separately when they are optional.

## Revenue stream 4: marketplace revenue share

A marketplace kit can generate revenue through a cloud or channel transaction.

The share depends on who sourced the customer and who operates the account.

Attribution must be stored in the partner portal before the transaction.

Revenue share applies to eligible Thinkery net revenue, not gross customer bill
amounts unless expressly agreed.

The contract must define refunds, credits, taxes, and marketplace fees.

### Marketplace share principles

Reward sourced demand more than passive listing.

Reward deployment and renewal support when the partner carries that work.

Protect Thinkery margin for high-touch support.

Review share rates by segment and actual partner contribution.

Do not allow multiple partners to claim the same opportunity indefinitely.

## Revenue stream 5: success fee

The success fee is based on proven savings or a defined operational outcome.

It requires a written baseline, measurement window, and attribution method.

It must account for changes in workload, model price, quality target, and
customer behavior.

It should be used when the partner can influence adoption and measurement.

It should not replace a sustainable platform fee.

### Success fee formula

Verified savings equals baseline cost minus governed cost, adjusted for scope.

Eligible savings excludes benefits caused only by model price changes.

Eligible savings excludes a quality reduction that violates the agreed target.

Success fee equals eligible savings multiplied by the agreed partner percentage.

The customer receives a transparent savings report before settlement.

## Hybrid commercial packages

A builder package can combine platform fee, included usage, and implementation
services.

An SI package can combine resale margin, certification, and success fee.

An MSP package can combine wholesale usage, support fee, and minimum commitment.

An embedded package can combine annual commitment, tenant fee, and usage.

A marketplace package can combine list price, private offer, and referral share.

Every package must identify the payer, seller, meter, renewal, and support owner.

## Pricing guardrails

Do not use a token meter that customers cannot independently reconcile.

Do not make the badge dependent on a hidden commercial upgrade.

Do not discount below supportable gross margin without an executive exception.

Do not offer success fees without measurement access.

Do not let a partner bundle Thinkery in a way that prevents customer disclosure.

Do not allow a partner to promise perpetual pricing without written approval.

## Partner discount ladder

Certified Builders receive enablement access, not automatic resale discount.

Silver Partners receive limited referral or resale economics.

Gold Partners receive stronger margin for repeatable deployments.

Platinum Partners receive co-sell economics tied to forecast and performance.

Discounts increase only when partner contribution and customer quality increase.

Benefits can be reduced when activity or quality falls below the tier standard.

## Illustrative unit economics

Assume one production agent has a platform fee of 1,000 units per month.

Assume included usage covers the customer’s agreed baseline.

Assume variable usage above the band creates 0.01 units per governed context
token.

Assume a partner delivers ten agents with one shared operations team.

The partner can earn services revenue while Thinkery earns recurring platform and
usage revenue.

The specific currency and prices are set by segment and contract.

These values illustrate the structure, not a customer quote.

## Partner margin example

A Silver Partner may earn a 10 percent referral share on eligible net revenue.

A Gold Partner may earn a 20 percent resale margin when it owns deployment.

A Platinum Partner may earn up to 30 percent on qualified sourced and supported
volume.

Higher margin requires documented delivery, support, and renewal contribution.

Thinkery retains the right to cap margin where support cost makes the deal
unprofitable.

## Success economics example

A customer establishes a baseline of 100,000 units for a defined workload.

The governed Thinkery path costs 65,000 units at an equivalent quality target.

Eligible savings are 35,000 units after agreed adjustments.

If the success share is 20 percent, the partner receives 7,000 units.

The platform fee remains payable because the platform continues to create value.

The contract records the evidence and measurement window before the pilot starts.

## Renewal and expansion economics

Renewal economics reward low incident rates and measured adoption.

Expansion economics reward additional agents, teams, regions, or governed
workloads.

A partner keeps attribution when it remains materially involved in the account.

Attribution can expire after a defined inactivity period.

Customers can renew directly if channel support no longer adds value.

The partner receives notice and a fair transition process.

## Revenue attribution rules

Register the opportunity before customer commercial discovery where possible.

Record source, influence, delivery, operations, and renewal roles separately.

Allow one primary source partner and multiple participating partners.

Define how marketplace and SI contributions interact.

Resolve attribution disputes with dated evidence, not account-owner preference.

Review multi-partner attribution in a deal desk.

## Economics by partner category

Builders monetize services, accelerators, and recurring resale margin.

Technology partners monetize adoption, retention, and ecosystem relevance.

Cloud marketplaces monetize transaction volume and cloud commitment.

MSPs monetize managed operations and recurring margin.

VARs monetize procurement, implementation, and account coverage.

Thinkery monetizes software, usage, governance, and measured expansion.

## Gross-margin protection

Track support hours by partner tier and integration.

Track inference and storage costs separately from platform costs.

Track discounts against lifetime gross profit, not first-year revenue alone.

Require an escalation for deals with unbounded usage.

Use customer budgets and rate limits as commercial controls.

Build standard diagnostic tools so partner support does not become bespoke
engineering.

## Partner profitability promise

The program should show a partner how to make money before asking for pipeline.

The partner profitability model includes services hours, sales cycle, margin,
support load, and renewal probability.

Thinkery should provide a calculator with conservative defaults.

The calculator should show downside as well as upside.

The partner should be able to compare Thinkery economics with building an
internal context layer.

The strongest pitch is a better business model, not a bigger feature list.
