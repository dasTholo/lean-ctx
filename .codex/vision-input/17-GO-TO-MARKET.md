# 1. EXECUTIVE GO-TO-MARKET STRATEGY
## 1.1 North-star outcome
## By month 18, LeanCTX is the default context-efficiency layer for AI-agent work
## The product is known first for savings, then for visibility, then for governance
## Individual developers experience value without a sales call
## Teams see savings by project, repository, model, and workflow
## Engineering leaders can explain AI-agent spend in operating-review language
## Enterprise buyers can deploy a Control Plane without surrendering source code
## Builders can package reusable Context Kits and distribute them through a marketplace
## The go-to-market engine deliberately moves from bottom-up proof to top-down control

## 1.2 Customer journey
## Stage one: discover waste through a concrete token-cost story
## Stage two: install the CLI through a trusted developer channel
## Stage three: run one workflow and see a savings report
## Stage four: invite teammates because the waste is shared
## Stage five: upgrade for shared insights, policy, and support
## Stage six: expand into governance, compliance, and fleet-level optimization
## Stage seven: build or buy Context Kits for repeatable agent deployments
## Each stage has a separate activation event and a separate owner
## No stage depends on a vague awareness metric
## The handoff from one stage to the next is visible in product analytics
## Sales follows usage evidence instead of replacing it

## 1.3 Market message architecture
## Category: context operating system for enterprise AI
## Practical wedge: context compression and token-efficiency for coding agents
## Economic value: lower model spend and faster agent completion
## Operational value: fewer repeated reads, fewer stalled runs, and clearer budgets
## Team value: shared visibility into what agents consume and why
## Enterprise value: govern, optimize, and prove ROI across the agent fleet
## Platform value: package proven context workflows for other builders
## Proof hierarchy: local report, team dashboard, controlled pilot, fleet benchmark
## Primary emotional benefit: relief from invisible waste
## Primary rational benefit: measurable savings with a reversible install
## Primary call to action: install lean-ctx and run the five-minute proof
## Secondary call to action: send a savings report to the team lead
## Tertiary call to action: schedule a savings review
## Enterprise call to action: start a paid pilot with a defined baseline
## Builder call to action: publish a Context Kit

## 1.4 Message rules
## Use “tokens” when speaking to developers
## Use “AI spend” when speaking to finance and engineering leadership
## Use “context efficiency” when speaking to platform and infrastructure teams
## Use “agent fleet governance” when speaking to enterprise buyers
## Use “production agent building blocks” when speaking to partners
## Use a specific workflow example in every launch asset
## Show raw input volume, compressed input volume, cost delta, and time delta
## Separate observed results from expected results
## Label all benchmark assumptions
## Keep “60-90%” as a hypothesis range until a cohort proves it
## Lead with five minutes to value rather than a feature inventory
## Lead with evidence rather than fear
## Avoid implying that all tokens are waste
## Avoid promising identical savings across models or repositories
## Avoid promising automatic quality improvement without a quality check
## Avoid naming competitors as villains
## Avoid using enterprise language in the first-run install experience

## 1.5 Funnel definitions
## Reach: a qualified developer sees a relevant savings example
## Intent: the developer opens the install or benchmark page
## Install: the package or binary is installed successfully
## Activation: a real agent workflow produces a local savings report
## Habit: the user generates at least two reports in fourteen days
## Advocacy: the user shares a report, issue, pull request, or referral
## Team signal: two or more users from one domain activate within thirty days
## Team activation: three weekly active users plus one shared dashboard
## Paid conversion: a team starts a paid subscription or a paid pilot
## Expansion: seats, repositories, workflows, or deployment scope increases
## Retention: the account has a measured workflow in the prior thirty days
## Revenue quality: gross retention, net retention, payback, and support load are tracked together
## Every dashboard uses these definitions without local reinterpretation
## Product analytics and CRM share one account identifier
## UTM naming maps to installation and workspace creation
## Self-reported savings are never mixed with instrumented savings

## 1.6 Instrumentation before promotion
## Emit an install event without collecting source code
## Emit an activation event when a report is generated
## Store model, workflow type, input tokens, output tokens, and compressed tokens only when consented
## Hash repository identity before any aggregate storage
## Provide a local-only mode that never sends usage telemetry
## Provide an exportable report for teams that cannot share data
## Version benchmark recipes so results remain comparable
## Tag every report with product version and model family
## Record whether savings came from compression, caching, routing, or repetition removal
## Capture quality checks alongside savings
## Capture latency before and after intervention
## Capture failure rate before and after intervention
## Build a public anonymized benchmark only from explicit opt-in data
## Make telemetry status visible in the CLI
## Document retention and deletion behavior
## Publish a measurement methodology before publishing headline savings
## Add a “why this number changed” panel to dashboards
## Assign data-quality ownership to product engineering
## Review metric integrity every two weeks

# 2. IDEAL CUSTOMER PROFILE AND SEGMENTATION
## 2.1 Phase-one individual developer
## Uses an AI coding agent at least three times per week
## Works in a repository larger than a toy project
## Notices repeated file reads, bloated prompts, or slow context gathering
## Can install a CLI without procurement approval
## Shares technical findings publicly or inside a team
## Values transparent local tooling
## Has authority to change their own agent workflow
## Wants a result in one sitting
## Is willing to share an anonymized report
## Likely role: staff engineer, tech lead, consultant, or OSS maintainer
## Trigger: a long agent run feels slow or expensive
## Objection: another tool adds setup and complexity
## Proof: five-minute report showing a real workflow delta

## 2.2 Phase-two team
## Has five to fifty developers
## Uses multiple AI coding or automation tools
## Has an engineering manager, platform lead, or developer-experience owner
## Receives an AI-tool budget or a visible model-spend line item
## Needs shared reporting rather than individual anecdotes
## Has enough repository variety to benefit from comparison
## Can approve a low-friction SaaS subscription
## Trigger: leadership asks where AI spend is going
## Objection: the team already has vendor dashboards
## Proof: workspace report tied to a project, sprint, or cost center
## Buying committee: champion, manager, security reviewer, budget owner
## Expansion trigger: second repository or second team asks for access

## 2.3 Phase-three enterprise
## Has fifty or more developers using agents
## Runs centralized engineering platforms or developer productivity programs
## Has security, privacy, or residency constraints
## Needs policy, auditability, or deployment control
## Has a measurable AI adoption initiative
## Can run a paid pilot with a named sponsor
## Trigger: AI spend grows faster than confidence in outcomes
## Objection: telemetry, vendor risk, and deployment friction
## Proof: controlled pilot with baseline and executive readout
## Buying committee: VP engineering, platform, security, finance, procurement
## Expansion trigger: additional business units, models, or regulated workloads

## 2.4 Phase-four builder
## Builds internal or external AI agents
## Wants repeatable context workflows
## Has a platform or solutions-engineering team
## Needs faster time from prototype to production
## Can publish reusable patterns or integrations
## Trigger: every agent project reinvents retrieval and context shaping
## Objection: marketplace quality and support uncertainty
## Proof: Context Kit deployed in days with a measurable time reduction
## Buying committee: platform leader, product leader, partner manager
## Expansion trigger: multiple kits, partner co-sell, marketplace revenue

## 2.5 Disqualification rules
## Do not prioritize a user with no agent workflow to measure
## Do not prioritize a team that cannot access any usage evidence
## Do not promise savings where quality cannot be tested
## Do not begin an enterprise pilot without a named sponsor
## Do not accept a marketplace partner without maintenance ownership
## Do not count a social follower as pipeline
## Do not count a free install as activation
## Do not count a logo without a measurable result
## Do not let one loud account define a segment
## Review disqualification patterns monthly
