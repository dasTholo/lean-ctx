# Brand Architecture for LeanCTX, Thinkery, and the Context Platform

Status: Agent 15 recommendation

Audience: founders, product, engineering, design, marketing, sales, and partners

Decision requested: approve the naming system before public product and domain work

Scope: parent brand, open source engine, commercial platform, kits, marketplace,
product-version names, positioning, visual identity, messaging, and domains

This document is intentionally operational.

Each name has a role.

Each role has a public form.

Each public form has a technical form where needed.

The system protects existing LeanCTX equity.

The system gives Thinkery room to become a company-scale product brand.

The system prevents ctxpkg from becoming an accidental customer-facing brand.

The system can survive additional products without inventing a new prefix every year.

## 1. Executive recommendation

Recommended architecture: Option B with a disciplined Thinkery endorsement layer.

Thinkery is the commercial masterbrand and ecosystem umbrella.

LeanCTX is the open source context engine.

Thinkery Platform is the integrated commercial product.

Thinkery Kits is the human-facing name for reusable context packages.

Thinkery Exchange is the curated marketplace.

Thinkery Registry is the machine-facing package index and distribution service.

ctxpkg remains a technical package format and compatibility namespace.

Do not promote ctxpkg to the primary marketplace or company brand.

Use the phrase powered by LeanCTX wherever technical credibility matters.

Use Thinkery as the first word in customer-facing commercial product names.

Use LeanCTX as the first word in open source repositories, APIs, and engine documentation.

Use Context Kit as the descriptive category name.

Use Thinkery Kits as the portfolio name.

Use Thinkery Exchange for discovery, commerce, certification, and distribution.

Use Thinkery Registry for the underlying index, API, and artifact service.

The complete relationship can be stated in one sentence.

Thinkery is the platform and ecosystem, powered by the open source LeanCTX engine.

The product stack is therefore:

Thinkery

Thinkery Platform

Thinkery Control

Thinkery Exchange

Thinkery Kits

LeanCTX

ctxpkg

This is a branded house with one technical endorsed brand.

It is not a collection of unrelated products.

It is not a rename of LeanCTX.

It is not a promise that every future feature must contain the word Thinkery.

## 2. The core brand idea

The category is context infrastructure for reliable AI agents.

The customer problem is not simply model intelligence.

The customer problem is deciding what an agent should know, when it should know it,
and how that knowledge can be governed.

The brand should therefore own the idea of intentional context.

Thinkery means a place where thought is prepared, organized, and made useful.

That meaning is warmer than infrastructure software.

LeanCTX means efficient context engineering.

That meaning is concrete for developers.

The two names can coexist if they answer different questions.

Thinkery answers: what business and product ecosystem should I buy into?

LeanCTX answers: what open source engine and implementation should I build with?

ctxpkg answers: what package format or artifact should my tools consume?

The naming system should never ask one name to answer all three questions.

## 3. Brand hierarchy

### 3.1 Level zero: company or corporate identity

Corporate name: use the legal entity selected by the founders.

Public masterbrand: Thinkery.

Thinkery should appear on the main website, product navigation, sales materials,
partner agreements, and commercial invoices.

Thinkery should not be described as an AI model.

Thinkery should not be described as an agent itself.

Thinkery should be described as context infrastructure for reliable AI agents.

The corporate identity may use a suffix such as Labs, Inc., GmbH, or Technologies.

The suffix is a legal and investor-facing matter.

The product-facing name should remain Thinkery unless legal review requires a change.

### 3.2 Level one: open source engine

Name: LeanCTX.

Role: the open source context-engineering core.

Short description: an open source engine for building, compressing, retrieving,
and governing context for AI agents.

Primary audience: developers, researchers, infrastructure teams, and open source
contributors.

Primary proof: source code, benchmarks, integrations, extension points, and release
notes.

Brand relationship: LeanCTX is an endorsed technical brand within the Thinkery
ecosystem.

Endorsement: LeanCTX by Thinkery.

Secondary endorsement: powers Thinkery Platform.

Do not rename the repository to Thinkery Engine merely for visual consistency.

Do not hide LeanCTX behind a generic term such as Context Core.

Do not force commercial billing, account, or cloud language into the open source
engine identity.

### 3.3 Level two: commercial platform

Name: Thinkery Platform.

Role: the integrated product for context operations across teams, agents, and
production environments.

Short description: the operating layer for governed agent context.

Primary audience: CTOs, platform engineering teams, AI product teams, and
enterprise architects.

Primary proof: reliability, governance, observability, policy controls, deployment
options, and measurable agent outcomes.

Use Platform as the suite name.

Use Control for the product surface that manages policy and operations.

Use Engine only when describing the implementation layer or the v1 capability.

### 3.4 Level three: reusable kits

Portfolio name: Thinkery Kits.

Category name: Context Kits.

Artifact name: Context Kit.

Technical package identifier: ctxkit where a new identifier is practical.

Compatibility namespace: ctxpkg.

Role: curated, versioned, portable bundles of context assets, policies, prompts,
schemas, connectors, evaluation cases, and metadata.

Thinkery Kits is approachable to buyers and partners.

Context Kit is clear in product education and documentation.

ctxpkg is compact for command-line flags, package manifests, and protocol docs.

Do not call the product CtxPacks in primary navigation.

Do not call the product AgentKits unless agents are always the package boundary.

### 3.5 Level four: marketplace and registry

Marketplace name: Thinkery Exchange.

Category descriptor: the Context Kit marketplace.

Registry name: Thinkery Registry.

Role of Exchange: discovery, evaluation, commerce, certification, reviews, and
partner distribution.

Role of Registry: package resolution, version metadata, artifact download, signing,
and machine-to-machine access.

The same kit can be discovered in Exchange and installed from Registry.

Exchange is a place and relationship.

Registry is a service and protocol.

This distinction prevents the marketplace name from being overloaded with backend
implementation language.

## 5. Naming rules

Use Thinkery for the product family customers can buy.

Use LeanCTX for the engine developers can run, extend, and inspect.

Use Context for the capability category.

Use Kit for a portable bundle.

Use Control for policy, administration, and operations.

Use Exchange for marketplace discovery and transactions.

Use Registry for machine delivery and version resolution.

Use ctxpkg only when discussing the existing format or protocol.

Use lowercase identifiers only in code, package manifests, URLs, and commands.

Use title case in product names.

Use sentence case in prose.

Do not add Cloud to every hosted feature.

Do not add AI to every name.

Do not add Agent to every name.

Do not add OS to the platform name until the product truly behaves like an
operating system for multiple agent runtimes.

Do not use Engine as a synonym for the entire company.

Do not use Platform as a synonym for a single API endpoint.

Do not use Marketplace as the name of the artifact registry.

Do not use Thinkery and LeanCTX as interchangeable adjectives.

## 6. One-line architecture explanation

LeanCTX supplies the engine.

Thinkery Platform turns the engine into a governed service.

Thinkery Kits package repeatable context.

Thinkery Control manages policy and operations.

Thinkery Exchange distributes trusted kits.

Thinkery Registry makes those kits installable.

This sentence should be memorized by every person who presents the product.

## 8. Why the recommendation is not a full rename

LeanCTX carries technical specificity.

LeanCTX signals context engineering rather than generic AI.

LeanCTX is suitable for an open source project with a focused contributor audience.

A rename would discard repository history, citations, package references, and
developer recognition.

A rename would also make it harder for users to understand what remains open source.

Thinkery carries emotional and commercial flexibility.

Thinkery can encompass workflow, governance, distribution, and services.

Thinkery can speak to both human judgment and machine context.

The combination creates a useful division of labor.

LeanCTX proves the technology.

Thinkery packages the experience.

The endorsed-brand relationship preserves attribution without forcing one name into
every context.

## 9. Public endorsement language

Preferred: Thinkery Platform, powered by LeanCTX.

Preferred: Thinkery builds context infrastructure on the open source LeanCTX engine.

Preferred: LeanCTX is the open source engine behind Thinkery Platform.

Acceptable: LeanCTX by Thinkery.

Use sparingly: Thinkery LeanCTX.

Avoid: Thinkery Engine is LeanCTX.

Avoid: LeanCTX Cloud.

Avoid: Thinkery is the commercial version of LeanCTX.

The commercial product is an operational layer, not merely a hosted binary.

## 10. Naming confidence and assumptions

The recommendation assumes Thinkery can be cleared for the relevant goods and
services.

The recommendation assumes the team wants open source credibility to remain visible.

The recommendation assumes ctxpkg already has implementation or community value.

The recommendation assumes a future kit ecosystem needs a name independent of
individual prompt templates.

The recommendation assumes the platform will include governance beyond retrieval.

If any assumption is false, the architecture can still be adapted through the
decision rules later in this document.

## 11. Option A: Thinkery as the umbrella

Option A makes Thinkery the visible name for every layer.

Thinkery Engine would be the commercial or technical engine label.

LeanCTX would be described as the implementation behind Thinkery Engine.

Thinkery Platform would be the full commercial product.

Thinkery Kits would be the package family.

Thinkery Marketplace would be the distribution surface.

### 11.1 Option A strengths

One prefix creates fast portfolio recognition.

Sales teams have one name to repeat.

The website can use a simple global navigation model.

The marketplace benefits from the trust built by the platform.

Future products can fit under Thinkery without new brand decisions.

The name sounds human and approachable.

The suite can speak to both agent builders and business operators.

The architecture is easy to explain to a new customer.

The parent brand can own a broad category over time.

Thinkery becomes an obvious noun for the company and the product.

### 11.2 Option A weaknesses

LeanCTX loses first-class public visibility.

Open source contributors may assume the engine is proprietary.

Developers may not find the repository when searching for LeanCTX.

Thinkery Engine is semantically vague.

Thinkery Marketplace is descriptive but not distinctive.

The prefix can become repetitive in documentation.

An umbrella brand may overpromise integration before the modules are mature.

The same name may need different trust signals for community and enterprise
audiences.

Thinkery is warm but may not immediately communicate context infrastructure.

All product failures can contaminate the open source project by association.

### 11.3 Option A naming risks

Thinkery Engine can be confused with a model or reasoning engine.

Thinkery Platform can sound like a generic consulting platform.

Thinkery Kits can sound like educational or craft kits.

Thinkery Marketplace can sound like a prompt-store clone.

The full system can feel consumer-oriented if visual identity is too playful.

The open source boundary can become unclear in pricing pages.

The name LeanCTX may appear as a footnote rather than a credible technology.

### 11.4 Option A mitigation

Keep LeanCTX in every developer-facing architecture diagram.

Use powered by LeanCTX in the primary product footer and developer hero.

Call the v1 capability Thinkery Context Engine, not Thinkery Engine alone.

Call the marketplace Thinkery Exchange, not Thinkery Marketplace.

Keep Context Kit as the category descriptor.

Publish a clear open source and commercial boundary page.

Use a technical sub-navigation for LeanCTX and ctxpkg.

### 11.5 Option A verdict

Option A is strongest for a single-company product portfolio.

Option A is weaker for open source identity and technical searchability.

Option A is viable if the company is committed to aggressive Thinkery brand
investment.

Option A should not erase LeanCTX.

Option A becomes materially better when the product names use distinct module nouns.

Recommendation: use the umbrella behavior of Option A without renaming the engine.

## 12. Option B: LeanCTX and Thinkery remain separate

Option B gives each name a clear job.

LeanCTX is the developer tool and open source engine.

Thinkery is the enterprise product and commercial ecosystem.

Thinkery Kits are domain packages for the platform.

Thinkery Exchange is the ecosystem marketplace.

The relationship is explicit but not merged.

### 12.1 Option B strengths

Open source users retain a clear project identity.

The technical engine can evolve independently of commercial packaging.

Thinkery can use enterprise language without making LeanCTX sound proprietary.

The platform can offer managed features beyond the open source core.

The architecture maps naturally to a freemium or open-core business.

Different audiences receive the vocabulary they need.

The engine name is more searchable among developers.

The commercial brand can expand into governance and distribution.

The endorsement relationship communicates technology provenance.

The model supports partners who build on LeanCTX without becoming Thinkery resellers.

### 12.2 Option B weaknesses

Two names require disciplined explanation.

Some buyers may ask whether LeanCTX is a separate company.

Product marketing needs a consistent powered by statement.

Sales collateral may need a small architecture diagram.

The platform may inherit any negative connotations of Thinkery separately from
LeanCTX.

Cross-product navigation can feel fragmented without strong information design.

People may casually abbreviate the platform as LeanCTX Cloud.

The company must maintain two communities with different expectations.

### 12.3 Option B naming risks

Separate names can appear like an acquisition or rebrand in progress.

Partners may publish incompatible combinations such as Thinkery Engine Kit.

The platform could be perceived as a thin hosted wrapper.

LeanCTX could be perceived as an internal dependency.

Thinkery Kits could be confused with a separate SDK.

The phrase Thinkery by LeanCTX would reverse the hierarchy.

### 12.4 Option B mitigation

Publish a canonical relationship sentence.

Use a stable architecture graphic everywhere.

Keep LeanCTX source, packages, and APIs visibly open.

Use Thinkery Platform for the commercial suite rather than a vague cloud suffix.

Name the integration surface LeanCTX Integration or LeanCTX Runtime.

Use Thinkery Control for commercial governance surfaces.

Use ctxpkg as a format and ctxkit as a package command only after compatibility
decisions are complete.

### 12.5 Option B verdict

Option B best protects long-term technical credibility.

Option B creates the cleanest open-core boundary.

Option B requires a higher communication standard.

The communication cost is small compared with the cost of a full technical rename.

Recommendation: select Option B as the formal architecture.

Use Thinkery as the endorsed commercial masterbrand.

Use LeanCTX as an independent but connected open source brand.

## 13. Option C: a new umbrella brand

Option C introduces a new parent name above LeanCTX and Thinkery.

The new name would signal an AI agent platform category.

LeanCTX would remain the engine under the hood.

Thinkery could become a product, studio, or internal codename.

Candidate families include AgentForge, ContextOS, AgentLayer, and other inventions.

### 13.1 Option C strengths

A new name can be designed for the intended category.

The parent can avoid inherited ambiguity from Thinkery.

The brand system can be clean from day one.

The name can be optimized for enterprise product positioning.

LeanCTX can remain a technical sub-brand.

Thinkery can become a creative product or community program.

The umbrella can be selected around a validated domain strategy.

The new name can signal an ambitious platform narrative.

### 13.2 Option C weaknesses

The company would discard any equity already built in Thinkery.

The new name needs explanation before it has meaning.

Category names are crowded and expensive to defend.

Agent language may age poorly as the market vocabulary changes.

The transition creates a long period of dual naming.

Search, social handles, documentation, and repositories need migration.

The name may sound like a framework rather than an operating platform.

The company would pay a branding tax before product-market fit is proven.

### 13.3 Option C decision criteria

Use a new umbrella only if Thinkery cannot be cleared legally.

Use a new umbrella only if research shows sustained confusion with another brand.

Use a new umbrella only if the target buyer rejects Thinkery as insufficiently
technical.

Use a new umbrella only if the existing team is ready to migrate every asset.

Use a new umbrella only if the new name has a defensible verbal distinction.

Use a new umbrella only if a domain and social identity are realistically
obtainable.

Use a new umbrella only if the category strategy requires a different promise.

Do not change names merely because a new name sounds more futuristic.

## 14. Option C candidate: AgentForge

AgentForge suggests construction, tooling, and industrial production.

It is easy to pronounce in English.

It gives developers an immediate build metaphor.

It may work for an SDK or agent development environment.

It is less natural for governance, context quality, and marketplace trust.

Forge language can imply code generation rather than context operations.

AgentForge is broad enough to attract unrelated competitors.

The name may be difficult to own in crowded technical categories.

The name risks over-centering agents instead of the context layer.

Pros: energetic, builder-friendly, memorable, action-oriented.

Cons: generic, developer-only, likely crowded, weak for trust and governance.

Verdict: suitable as an internal initiative or a builder module, not recommended
as the masterbrand.

## 15. Option C candidate: ContextOS

ContextOS signals a foundational layer.

It explains that context is a system concern rather than a prompt trick.

It can support APIs, storage, policy, and runtime features.

It is direct for technical buyers.

The OS suffix creates a strong category claim.

The OS suffix can sound inflated before the platform has broad adoption.

The name may be confused with an operating system, desktop product, or model layer.

ContextOS does not carry the warmth or human judgment suggested by Thinkery.

The name risks sounding like a generic infrastructure startup.

Pros: clear category, technical, extensible, architecture-friendly.

Cons: crowded suffix, overclaiming risk, less human, weak community warmth.

Verdict: useful as a positioning phrase, not recommended as the masterbrand.

## 16. Option C candidate: AgentLayer

AgentLayer implies an infrastructure layer beneath agents.

It communicates a role in a stack.

It can encompass context, tools, policy, and orchestration.

It is easy to explain in an architecture diagram.

The term AgentLayer is highly descriptive and therefore hard to differentiate.

It may be mistaken for an agent networking protocol.

It emphasizes agents rather than the durable context problem.

The name has low emotional distinctiveness.

Pros: architecture clarity, enterprise neutrality, extensible scope.

## 19. Final decision on the three options

Select Option B as the architecture.

Borrow Option A's simple commercial prefix discipline.

Reject Option C for the current phase.

## 20. The role of ctxpkg

ctxpkg is valuable as a technical shorthand.

ctxpkg is not a strong first-impression brand.

ctxpkg is difficult to pronounce consistently.

ctxpkg is visually compact in terminals and package manifests.

ctxpkg communicates package mechanics rather than customer value.

ctxpkg can remain a file extension, protocol, or compatibility namespace.

The marketplace should sell Context Kits, not ctxpkgs.

The docs should explain that a Context Kit may be distributed as a ctxpkg artifact.

The CLI can use ctxpkg if existing commands make that the least disruptive choice.

If a new package command is introduced, prefer ctxkit for readability.

Migration guidance: ctxkit consumes, produces, or wraps ctxpkg as compatibility
requires.

Never create both ctxpkg and ctxkit as competing public concepts without a clear
format-versus-product explanation.

## 21. Package naming model

Human category: Context Kit.

Portfolio label: Thinkery Kits.

Artifact type: ctxpkg.

Optional new CLI noun: ctxkit.

Example kit title: Security Review Context Kit.

Example package slug: security-review.

Example fully qualified package: thinkery/security-review.

Example registry path: registry.thinkery.[tld]/thinkery/security-review.

Example marketplace title: Security Review Context Kit.

Example developer reference: install the thinkery/security-review ctxpkg.

The title should describe the job.

The slug should be short, stable, and lowercase.

The package manifest should carry the brand, version, license, provenance, and
compatibility metadata.

The package name should not encode a temporary model vendor.

The package name should not encode a customer name without permission.

## 22. Product naming system across versions

The version labels describe capability maturity.

The marketing names describe what users can accomplish.

The technical release names may remain in changelogs and API documentation.

Do not make customers learn a new brand at every version.

Use one stable suite name with expanding modules.

### 22.1 v1: Context Engine

Recommended marketing name: Thinkery Context Engine.

Short name: Context Engine.

Technical attribution: powered by LeanCTX.

Primary promise: make agent context efficient, relevant, inspectable, and
repeatable.

Developer explanation: the engine assembles and compresses the right context for
an agent at the right time.

CTO explanation: a reliable context layer that improves agent quality without
requiring each team to invent its own memory and retrieval stack.

Why the name works: it is descriptive, credible, and honest about the first
capability.

Why it should not be Thinkery Engine: Context Engine names the customer problem,
while Engine alone is too broad.

Alternative v1 name: Thinkery Foundation.

Foundation sounds stable and strategic.

Foundation is less clear for developers searching for context features.

Alternative v1 name: Thinkery Runtime.

Runtime suggests production execution.

Runtime may understate indexing, policy, and preparation capabilities.

Alternative v1 name: Thinkery Context Runtime.

Context Runtime is technically precise.

Context Runtime sounds lower-level than the first marketing surface needs.

Alternative v1 name: Thinkery Signal Engine.

Signal Engine is memorable and useful for future data products.

Signal Engine does not immediately explain context engineering.

v1 verdict: Thinkery Context Engine.

Category label: Context Kits.

Technical artifact: ctxpkg.

Alternative v2 name: Thinkery AgentKits.

## 23. Release naming convention

Use product names for capabilities.

Use semantic versions for APIs and packages.

Use year or quarter labels only for commercial plans and launch campaigns.

Avoid making v1, v2, v3, v4, and v5 visible as separate brands.

Recommended external phrasing: Thinkery Platform now includes Thinkery Control.

Recommended release phrasing: the Context Kits release adds signed package
provenance.

Recommended technical phrasing: LeanCTX 1.x supports ctxpkg schema 1.

Avoid phrasing: buy Thinkery v5.

Avoid phrasing: upgrade from Thinkery Engine to Thinkery Marketplace.

The product should feel like one platform gaining capabilities.
